# Main Window UI Requirements — Secure Channels List

## Purpose
This document defines the behavior, visual hierarchy, and state management of the Main Window's primary UI component: the "Secure Channels" list. It details how the list reacts to user actions, Simulator events, and specifically defines the UI required to test both directions of handshakes across Direct and Relayed transport layers.

## Core Architecture
1. **Single Unified List:** All active text interactions (Direct P2P, Relayed, and Group) live in a single list.
2. **Recency Sorting:** The list is strictly sorted dynamically by `lastUpdate` timestamp in descending order (newest activity at the top).
3. **Naming Convention:** The list represents established E2EE sessions and is conceptually referred to as "Secure Channels".

## Visual Hierarchy & Metadata
Each entry in the Secure Channels list must display:
- **Avatar:** Initials for 1:1 peers, or a multi-user icon for groups.
- **Name:** The display name of the peer or group.
- **Tech Badge:** A small, visually distinct tag indicating the transport layer:
    - `DIRECT` (Emerald Green)
    - `RELAY` (Amber)
    - `GROUP` (Purple)
    - `PENDING` (Cyan/Blue)
- **Last Message Snippet:** A truncated string of the most recent payload (inbound or outbound) or system status.
- **Unread Badge:** A highlighted count of unread messages.
- **Online Indicator:** (For 1:1 only) A glowing dot if the peer is currently reachable.

## Connection Management UI (Handshakes & Invites)
To keep the Main Window neat and tidy, all handshake initiation and acceptance actions are consolidated into a single "Connection Management" modal.
- **Trigger:** A single `UserPlus` (or similar network/add) button in the Main Window header.
- **Notification Behavior:** If there are unaccepted inbound requests, this button pulses and displays a notification count badge.
- **Default Focus:** Clicking the button opens the modal. If there are pending inbound requests, it defaults to Tab 1. Otherwise, it defaults to Tab 2.

This modal contains three tabs:

### Tab 1: Incoming Signals (Inbound Requests)
**Anti-Spam Protocol:** Unaccepted incoming handshakes must **never** appear in the main Secure Channels list.
- **Content:** A list of pending `X3DH_INIT` payloads queued by the Simulator and targeting the Main Node.
- **List Item Details:** Each pending request must show the Peer Name and the **Transport Route** (e.g., *"Arriving via: Vanguard_Relay"* or *"Arriving via: Direct P2P"*) to allow transport verification during testing.
- **Actions:** `[ACCEPT]` and `[BURN/REJECT]` buttons.
- **Resolution:** Clicking Accept queues an `X3DH_ACCEPT` payload. The channel then migrates into the main Secure Channels list.

### Tab 2: Network Search (Manual Outbound Initiation)
Allows testing of explicit routing mechanisms from the Main Node to a Simulator Peer.
- **Input:** Target Identity (PKH).
- **Dropdown - Route Selection:** Crucial for simulator testing. Allows the user to explicitly select the transport mechanism:
    - `Direct P2P (Local Mesh)`
    - `[Active Relay Node Name A]`
    - `[Active Relay Node Name B]`
- **Action:** "Search & Connect" button. Triggers the creation of a `PENDING` channel in the main list and queues the `X3DH_INIT` payload.

### Tab 3: Import Token (OOB Initiation)
Allows testing of Out-of-Band (offline) invitations.
- **Input:** A textarea for pasting an opaque Base64 invite token generated by the Simulator.
- **Action:** "Decode & Initiate" button. Routing is automatically derived from the token's decoded contents. Creates a `PENDING` channel in the main list.

## Outbound Feedback Protocol
Requests initiated by the local user (via Tab 2 or 3) must appear in the main Secure Channels list immediately to provide an anchor for the pending action.
- **UI Behavior:** A new entry appears at the top of the list in a `PENDING` state.
- **Resolution:** - **Success:** When the Simulator delivers the `X3DH_ACCEPT` payload back to the Main Node, the channel fully activates and receives its permanent `DIRECT` or `RELAY` badge based on the route chosen.
    - **Failure/Timeout:** If the handshake expires, the state updates to `EXPIRED`.

## Secure Channel States & Main View Display
When a user clicks on a channel in the list, the Main View (right pane) updates to reflect the selected channel's specific state.

### State 1: PENDING (Outbound Request)
- **Trigger:** Handshake initiated, waiting for peer to accept.
- **Header:** Shows peer name, PKH, and a `PENDING` badge. Uplink/Inspector button is disabled.
- **Message History:** Empty, except for a prominent centered status banner: *"Establishing secure channel... Awaiting peer acceptance."* with a loading spinner.
- **Input Area:** Disabled/Greyed out. User cannot type until the channel is secure.

### State 2: ACTIVE (1:1 Direct or Relayed)
- **Trigger:** Handshake is complete (`X3DH_ACCEPT` delivered).
- **Header:** Shows peer name, PKH, `DIRECT`/`RELAY` badge, and an active Online indicator (green dot). Uplink button is active.
- **Message History:** Displays a system banner *"E2E Encryption Established • Session Active"*, followed by the chat history.
- **Input Area:** Fully enabled. Attachments, Emoji, and Send buttons are active.

### State 3: ACTIVE (Group)
- **Trigger:** Group invite payload delivered and processed.
- **Header:** Shows Group Name, member count, and a `GROUP` badge.
- **Message History:** Displays a system banner *"Group Encrypted Channel Established"*. Interleaves standard chat messages with System Messages (e.g., *"Sender Key Epoch advanced to 4"*).
- **Input Area:** Fully enabled.

### State 4: OFFLINE (1:1 Peer Disconnected)
- **Trigger:** Simulator toggles peer to 'Offline'.
- **Header:** Online indicator turns grey/red.
- **Message History:** Existing history remains visible. A warning banner appears at the bottom: *"Peer is offline. Messages will be queued."*
- **Input Area:** Enabled, but sending a message immediately marks it visually as 'Queued' rather than 'Sent'.

### State 5: EXPIRED / FAILED
- **Trigger:** Handshake times out or is explicitly rejected/force-expired by the Simulator.
- **Header:** Shows peer name, PKH, and a red `FAILED` badge.
- **Message History:** Centered error banner: *"Handshake failed or connection expired."*
- **Input Area:** Hidden entirely. Replaced with action buttons: `[Retry Connection]` and `[Delete Channel]`.

## Message Delivery States
Individual messages within the Message History display icon indicators based on their transport and cryptographic status:
- **Sent:** A single grey checkmark (Payload handed to local network stack).
- **Delivered:** Double grey checkmarks (Payload reached the target node).
- **Read:** Double cyan/blue checkmarks.
- **Failed:** A red "X" icon (Network unreachable or timeout).
- **Corrupted:** A visually simple, minimalist red warning triangle or broken-lock icon next to the message bubble.
    - *Interaction:* Hovering over the corrupted icon reveals a detailed tooltip (e.g., *"Decryption Failed: MAC verification error. The payload may have been tampered with or the ratchet is out of sync."*)

## Uplink Inspector UI
Toggled via the "Uplink" button in the active channel's Header. This slides out a visually appealing side-panel providing a high-level overview of the connection topology:
- **Direct (P2P):** Displays a simple straight-line node visualization: `[Operator Node] <====> [Peer Name]`.
- **Relayed:** Displays an angled or multi-step visualization: `[Operator Node] ----> [Relay Name] ----> [Peer Name]`.
- **Group:** Displays a hub-and-spoke visualization with the Group Name in the center branching out to active participants.

## Session Reset / Recovery
In the event a Double Ratchet session becomes desynchronized (evidenced by repeated "Corrupted" message states), users need a way to heal the session without losing the channel history.
- **Location:** A standard kebab/options menu (⋮) in the top-right corner of the Active Channel Header.
- **Action:** Contains a "Reset Secure Session" button.
- **Behavior:** Clicking this silently generates and queues a new `X3DH_INIT` payload for the target peer behind the scenes. It creates a temporary system message in the chat: *"Re-establishing secure connection..."* until the peer automatically accepts and the ratchets are realigned.
