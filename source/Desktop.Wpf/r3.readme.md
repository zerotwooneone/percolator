# R3 for WPF — Engineering Guide

This document distills the R3 documentation into a WPF-focused technical standard for Desktop.Wpf. It defines our reactive MVVM architecture, ensuring high performance, thread safety, and clean code separation using R3 and `ObservableCollections.R3`.

---

## 1) Architectural Boundaries (The MVVM Core)

To prevent "spaghetti state" and keep our application scalable, we strictly enforce boundaries between domain logic, background processes, and the WPF UI.

* **The Model (Pure Domain State)**
  * **Role:** Thread-agnostic data containers.
  * **Rule:** Models (e.g., `PeerModel`) **must not** contain WPF-specific types like `BindableReactiveProperty`. They hold state using `ReactiveProperty<T>`.
  * **Rule:** Models **must not** know about tracking, saving, or the UI thread. They are pure data mutated by background tasks.
* **The Service (The Source of Truth)**
  * **Role:** Singleton managers that own models and run background simulations.
  * **Rule:** Services hold collections of models using `ObservableList<T>`.
  * **Rule:** Services expose their state strictly via `ReadOnlyObservableList<T>`. Do not put UI-specific filtering methods (e.g., `GetActivePeers()`) on the service interface.
* **The ViewModel (The UI Bridge)**
  * **Role:** The layer that projects domain state into the WPF Dispatcher.
  * **Rule:** ViewModels wrap domain properties into `BindableReactiveProperty<T>`.
  * **Rule:** ViewModels are solely responsible for filtering collections and marshaling cross-thread updates to the UI.

## 2) Style Guide & Clean Code Conventions

Consistency in reactive code is critical for readability and preventing memory leaks.

### Naming Conventions
* **Bindable Properties:** Standard PascalCase. Do not use suffixes like `Prop` or `Observable` (e.g., `SearchText`, `IsConnected`).
* **Commands:** Always suffix with `Command` (e.g., `SaveCommand`, `DisconnectPeerCommand`).
* **Raw Observables (Events):** Use an action-oriented name indicating a stream (e.g., `OnPeerAdded`, `ConnectionStateChanged`).
* **Internal Subjects:** Prefix with an underscore and suffix with `Subject` (e.g., `_saveTriggerSubject`).

### The "Read-Only Instance" Rule
To prevent silently breaking WPF XAML bindings, all `BindableReactiveProperty` and `ReactiveCommand` properties **must be get-only**. Never replace the property instance; only update its `.Value`.

```csharp
// ❌ BAD: Replacing the instance breaks the XAML binding
public BindableReactiveProperty<string> Status { get; set; }

// ✅ GOOD: The binding remains intact
public BindableReactiveProperty<string> Status { get; }
```

### The `Unit` Rule for Triggers
If an observable exists purely to signal that an event happened (and carries no meaningful payload), it **must** be typed as `Observable<Unit>`. Never use `Observable<bool>` or `Observable<object>` for simple triggers. Use `.Select(_ => Unit.Default)` to normalize streams before merging.

### The Code-Behind Boundary
Do not write `Subscribe` blocks in `.xaml.cs` files. If a UI event (like `Window.Closing` or `ScrollViewer.ScrollChanged`) needs to enter the reactive pipeline, route it to a `ReactiveCommand` on the ViewModel.

## 3) Core Types & Error Model

* **Reliable Error Behavior:** Unlike legacy Rx, R3 does not tear down pipelines on errors. Exceptions surface to `OnErrorResume(Exception)`, allowing long-running UI streams to survive transient failures.
* **Terminal States:** Completion carries a `Result` (`Success|Failure`). Use `OnErrorResumeAsFailure()` if you explicitly want an error to terminate the stream.
* **Subject Disposal:** Disposing an R3 subject issues `OnCompleted` by default, unsubscribing all downstream observers and preventing leaks.

## 4) Threading & Synchronization (The Dispatcher Bridge)

Because our WPF app maintains continuous backend state, models frequently mutate on background threads. **It is the ViewModel's exclusive responsibility to synchronize these changes to the UI thread.**

### The Operator Ordering Rule: Filter Early, Marshal Late
Always apply filtering, distinct checks, and time-based pacing *before* marshaling to the UI thread. This protects the WPF Dispatcher from processing unnecessary updates.

### The Standard Bridge
Use `ObserveOnCurrentSynchronizationContext()` right before converting to a bindable property.

```csharp
Status = model.Status
    .DistinctUntilChanged() // Filter early
    .ObserveOnCurrentSynchronizationContext() // Marshal late
    .ToBindableReactiveProperty()
    .AddTo(ref _bag);
```

### The "Firehose" Problem
If a background simulation updates a value rapidly (e.g., 1,000 times a second), pushing all updates to the UI thread will starve the Dispatcher and freeze the app.

**Solution:** Pace the updates using `Sample` or `ThrottleLast` *before* the context switch.

```csharp
// Limit UI updates to roughly 60 FPS (16ms)
ActiveConnections = model.ActiveConnections
    .Sample(TimeSpan.FromMilliseconds(16))          // 1. Pace the background thread
    .ObserveOnCurrentSynchronizationContext()       // 2. Marshal safely to WPF
    .ToBindableReactiveProperty()                   // 3. Bind to XAML
    .AddTo(ref _bag);
```

## 5) Exposing & Filtering Collections

Do not write custom collection synchronization logic. Use `ObservableCollections.R3` to handle lists cleanly from the background down to the UI.

### In the Service (Source of Truth)
```csharp
public class PeerSimulationService 
{
    private readonly ObservableList<PeerModel> _peers = new();
    
    // Expose as read-only. No UI filtering logic here.
    public ReadOnlyObservableList<PeerModel> Peers => _peers.AsReadOnly();
}
```

### In the ViewModel (UI Projection & Filtering)
Use the `CreateView()` operator to map domain models to ViewModels, applying dynamic filters safely.

```csharp
public class PeerListViewModel : IDisposable
{
    public BindableReactiveProperty<string> SearchText { get; }
    public ReadOnlyObservableList<PeerDetailViewModel> FilteredPeers { get; }
    private DisposableBag _bag;

    public PeerListViewModel(PeerSimulationService service)
    {
        SearchText = new BindableReactiveProperty<string>("").AddTo(ref _bag);

        // Normalized trigger using Unit
        var filterTrigger = SearchText.Select(_ => Unit.Default);

        FilteredPeers = service.Peers
            .CreateView(
                selector: model => new PeerDetailViewModel(model), 
                filter: vm => vm.Name.Value.Contains(SearchText.Value), 
                recalculateFilterTrigger: filterTrigger 
            )
            .AddTo(ref _bag);
    }
    
    public void Dispose() => _bag.Dispose();
}
```

## 6) Commands & Async Execution

`ReactiveCommand` exposes `CanExecute` as an observable boolean and integrates directly with WPF bindings.

Combine commands with `SubscribeAwait` to handle asynchronous operations (like saving or network calls) with built-in backpressure strategies (e.g., `Drop` to prevent double-clicks).

```csharp
public ReactiveCommand SaveCommand { get; }

public ProfileViewModel() 
{
    SaveCommand = IsValid.ToReactiveCommand();
    
    SaveCommand.AsObservable()
        .SubscribeAwait(async (_, ct) => 
        {
            await profileService.SaveAsync(Model, ct);
        }, AwaitOperation.Drop) // Ignores subsequent clicks while saving
        .AddTo(ref _bag);
}
```

## 7) Background Operations & Persistence

When running background tasks, avoid mixing domain state with application tracking logic. Use Tracker classes to monitor state changes.

### Recipe: Debounced Saves without Polluting the Model
Extract the logic that dictates when a model is "dirty" into a dedicated tracker.

```csharp
// 1. Pure Model (Knows nothing about saving)
public class PeerModel : IDisposable {
    public ReactiveProperty<string> Status { get; } = new("Init");
    public void Dispose() => Status.Dispose();
}

// 2. The Tracker (Defines what constitutes a state change)
public class PeerSaveTracker : IDisposable {
    public PeerModel Peer { get; }
    public Observable<Unit> IsDirty { get; }
    private DisposableBag _bag;

    public PeerSaveTracker(PeerModel peer) {
        Peer = peer;
        IsDirty = peer.Status.Select(_ => Unit.Default);
    }
    public void Dispose() => _bag.Dispose();
}

// 3. The Service (Executes the debounced background save)
public void RegisterPeer(PeerModel peer) {
    var tracker = new PeerSaveTracker(peer).AddTo(ref _bag);
    
    tracker.IsDirty
        .Debounce(TimeSpan.FromSeconds(2))
        .SubscribeAwait(async (_, ct) => 
        {
            await SaveToDiskAsync(tracker.Peer, ct);
        }, AwaitOperation.Drop)
        .AddTo(ref _bag);
}
```

## 8) Subscription Management & Testing

### View/ViewModel Lifetimes
Long-lived services will leak ViewModels if subscriptions aren't severed. ViewModels must implement `IDisposable` and maintain a `DisposableBag` (a lightweight struct).

```csharp
public sealed class ChatViewModel : IDisposable
{
    private DisposableBag _bag; // Struct, do not instantiate with 'new'

    public ChatViewModel() 
    {
        // ... subscriptions AddTo(ref _bag)
    }

    public void Dispose() => _bag.Dispose();
}
```
*Ensure your Views dispose of their `DataContext` during the `Unloaded` or `Closed` events.*

### Testing with TimeProvider
R3 removes `IScheduler` overhead. Time is driven by `TimeProvider`. Use `FakeTimeProvider` from `Microsoft.Extensions.TimeProvider.Testing` for deterministic unit testing of time-based operators like `Debounce` or `Sample`. Convert streams to `.ToLiveList()` for allocation-free assertions.

## 9) Persistence & The Repository Pattern

To achieve **Persistence Ignorance**, the Domain and Service layers must never interact directly with database entities, ORM objects, or JSON serialization DTOs.

* **Rule 1: No Persistence Types in Services:** The Service layer only operates on pure Domain Models (e.g., `PeerModel`). It must not know about things like `[JsonProperty]`, `[Table]`, or database primary key nuances.
* **Rule 2: The Repository Interface:** Services persist data by depending on interfaces (e.g., `IPeerRepository`). The interface accepts and returns pure Domain Models.
* **Rule 3: The Infrastructure Boundary:** The concrete implementation of the repository lives in an Infrastructure layer. It is solely responsible for mapping the Domain Model to the Persistence DTO and performing the I/O operations.

### Example Architecture

**1. The Interface (Domain Layer)**
```csharp
public interface IPeerRepository
{
    // Accepts pure models
    ValueTask SaveAsync(PeerModel peer, CancellationToken ct);
    ValueTask<PeerModel?> LoadAsync(Guid id, CancellationToken ct);
}
```

**2. The Service (Domain Layer)**
```csharp
public class PeerSimulationService
{
    private readonly IPeerRepository _repository;

    public PeerSimulationService(IPeerRepository repository)
    {
        _repository = repository; // Injected via DI
    }

    // The service orchestrates the domain models, completely unaware of how they are saved.
}
```

**3. The Implementation (Infrastructure Layer)**
```csharp
public class JsonPeerRepository : IPeerRepository
{
    public async ValueTask SaveAsync(PeerModel peer, CancellationToken ct)
    {
        // 1. MAP: Convert the pure domain model into a flat, serialization-friendly DTO.
        var dto = new PeerPersistenceDto 
        {
            Id = peer.Id,
            Status = peer.Status.Value // Extract the raw value from the ReactiveProperty
        };

        // 2. SAVE: Perform the actual I/O.
        await File.WriteAllTextAsync($"{dto.Id}.json", JsonSerializer.Serialize(dto), ct);
    }
}

// Hidden entirely from the rest of the application
internal class PeerPersistenceDto
{
    public Guid Id { get; set; }
    public string Status { get; set; } = "";
}
```
