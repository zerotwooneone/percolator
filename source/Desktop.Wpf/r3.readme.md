# R3 for WPF — Engineering Guide

This document distills the massive R3 documentation into a WPF-focused, technical guide we will grow in sections. It explains how and why we will use R3 inside Desktop.Wpf.

---

## 1) Overview and Why R3 (vs System.Reactive/UniRx)

- **What R3 is**
  - A modern re-implementation of Reactive Extensions for .NET with a new core (`Observable<T>`, `Observer<T>`) and high performance.
  - Optimized for UI apps and games; removes `IScheduler` in favor of `.NET 8 TimeProvider` and adds frame-based APIs.
- **Why use it in WPF**
  - **Reliable error behavior**: R3 does not tear down pipelines on errors. Exceptions are surfaced to `OnErrorResume(Exception)` and completion carries a `Result` (`Success|Failure`). This matches long-running UI streams where teardown on transient errors is undesirable.
  - **Performance**: No `IScheduler` overhead; minimal allocations for subjects and disposables; efficient subscription tracking to prevent leaks.
  - **UI binding first-class**: `BindableReactiveProperty<T>` exposes observable state that binds to XAML via `.Value`, removing manual `INotifyPropertyChanged` plumbing.
  - **Time control**: Uses `TimeProvider` (and optional `DispatcherTimeProvider` for WPF) giving deterministic timers and easy testing with `FakeTimeProvider`.
  - **Async/await integration**: `SelectAwait/WhereAwait/SubscribeAwait` let us compose async work (I/O, decryption) without blocking the UI, with backpressure strategies like `Sequential`, `Drop`, `Switch`, `Parallel`.
- **How it differs from legacy Rx**
  - Errors go to `OnErrorResume`, stream continues. Completion is a single `OnCompleted(Result)` instead of `OnCompleted`/`OnError` split.
  - Time is driven by `TimeProvider` (and frame by `FrameProvider`), not `IScheduler`.
  - Subjects are tuned for low allocation and predictable disposal—disposing completes subscribers by default.
- **Package(s) to install**
  - Core: `R3`
  - Testing: `Microsoft.Extensions.TimeProvider.Testing` (for `FakeTimeProvider`); `R3` includes its own `FakeFrameProvider`.
  - Optional collections: `ObservableCollections.R3` if we need reactive lists/dictionaries.
- **Targeting/compat**
  - Works on .NET 8/9. Our WPF project targets .NET 9, so we’re aligned.
- **Binding convention we adopt (per Desktop.Wpf/readme.md)**
  - ViewModels expose `BindableReactiveProperty<T>` and XAML binds to `.Value`.
  - Example:
    ```csharp
    public BindableReactiveProperty<string> MessageInput { get; }
    public BindableReactiveProperty<bool> CanSend { get; }

    MessageInput = new("");
    CanSend = MessageInput
        .Select(text => !string.IsNullOrWhiteSpace(text))
        .ToBindableReactiveProperty(false);
    ```
    ```xml
    <TextBox Text="{Binding MessageInput.Value, UpdateSourceTrigger=PropertyChanged}" />
    <Button IsEnabled="{Binding CanSend.Value}" />
    ```
- **Where it fits our architecture**
  - Drives feature ViewModels (Chat, Sessions) with reactive state and commands.
  - Background work is hosted in `IHostedService`; UI subscriptions use `ObserveOn` the WPF `SynchronizationContext` or a `DispatcherTimeProvider` when updating bound state.

> Next sections will deep-dive core types, error/completion model, WPF dispatcher/time providers, binding patterns, commands, subscription management, threading, testing, migration, and recipes.

## 2) Core types and error/completion model

- **Core contracts**
  - `Observable<T>`: the stream source. Subscribed via `IDisposable Subscribe(Observer<T> observer)` and operator extensions.
  - `Observer<T>`: receives events with three methods:
    - `OnNext(T value)`
    - `OnErrorResume(Exception error)` — error surfaced but the subscription is NOT cancelled.
    - `OnCompleted(Result result)` — one terminal signal carrying `Result.Success` or `Result.Failure(Exception)`.
  - Rationale: UI streams should not auto-teardown on incidental errors; we often want to display an error and continue.

- **Result semantics**
  - `Result` is a struct with `IsSuccess/IsFailure` and optional `Exception`.
  - Shorthands exist: `observer.OnCompleted()` => success, `observer.OnCompleted(exception)` => failure.
  - Operators that produce terminal conditions convert to `OnCompleted(Result)`; consumers centralize success/failure handling in one place.

- **Error handling patterns**
  - Default pipeline continues after `OnErrorResume`. Use one of these when you need stop-on-error behavior:
    - `OnErrorResumeAsFailure()` — converts error to `OnCompleted(Exception)` to terminate the stream.
    - `DoCancelOnCompleted(cts)` — for hot sources like `Range` with `CancellationToken`, ensures upstream is cancelled when downstream completes.
  - Unhandled errors path: if an exception reaches the end (no handler), R3 calls `ObservableSystem.RegisterUnhandledExceptionHandler(...)` handler. Hook this to our `ILogger`.

- **Subjects and disposal**
  - Provided subjects: `Subject`, `BehaviorSubject`, `ReactiveProperty`, `ReplaySubject`, `ReplayFrameSubject`.
  - Design choice: disposing a subject issues `OnCompleted` by default, unsubscribing all downstream observers (prevents leaks). If you must avoid completion, call `Dispose(false)`.
  - `ReactiveProperty<T>` is a state holder with `.Value` and duplicate-suppression. Use `ReadOnlyReactiveProperty<T>` for read-only exposure.

- **Async/await integration**
  - Async-aware operators: `SelectAwait`, `WhereAwait`, `SubscribeAwait` with `AwaitOperation` strategies:
    - `Sequential` (queue), `Drop` (debounce clicks), `Switch` (latest wins), `Parallel`, `SequentialParallel`, `ThrottleFirstLast`.
  - Methods that yield a single value return `Task<T>` (e.g., `FirstAsync`, `LastAsync`). If an error occurs, the returned task is faulted.

- **Interop**
  - Convert between legacy `IObservable<T>` and R3:
    - `IObservable<T>.ToObservable()` -> `Observable<T>`
    - `Observable<T>.AsSystemObservable()` -> `IObservable<T>`

- **WPF-specific guidance**
  - Keep UI-bound streams alive; prefer surfacing errors via `OnErrorResume` and mapping them to validation or toast notifications.
  - For truly terminal conditions (e.g., session disposed), explicitly end with `OnCompleted(Exception)` via `OnErrorResumeAsFailure()`.
  - Always own subscriptions with a disposable container (see Section 6) to align with window/view lifetimes.

## 3) TimeProvider/FrameProvider and WPF integration

- **Why no IScheduler**
  - R3 removes `IScheduler`; time-based operators receive a `.NET TimeProvider` argument or use `ObservableSystem.DefaultTimeProvider`.
  - Benefits: fewer allocations, simpler testing (fakeable clock), consistency across platforms.

- **Defaults and configuration**
  - By default R3 uses `TimeProvider.System`.
  - You can override globally:
    ```csharp
    using R3;
    ObservableSystem.DefaultTimeProvider = TimeProvider.System; // keep default or swap
    // Optionally, hook unhandled errors to our logger
    ObservableSystem.RegisterUnhandledExceptionHandler(ex => logger.LogError(ex, "R3 Unhandled"));
    ```

- **DispatcherTimeProvider (UI thread alignment)**
  - For WPF, timers often need to marshal back to the UI thread. Use a dispatcher-backed provider when producing UI-facing values.
  - Pattern:
    ```csharp
    // during App startup or Shell initialization
    var dispatcherTp = DispatcherTimeProvider.FromCurrentDispatcher();
    ObservableSystem.DefaultTimeProvider = dispatcherTp; // optional — or pass per-operator
    ```
  - Per-use example without changing the global default:
    ```csharp
    var ui = DispatcherTimeProvider.FromCurrentDispatcher();
    Observable.Interval(TimeSpan.FromSeconds(1), ui)
      .Subscribe(x => TickCount.Value = x);
    ```

- **Common time-based operators**
  - `Interval(TimeSpan, TimeProvider)` — periodic events.
  - `Delay/DelaySubscription(TimeSpan, TimeProvider)` — schedule later.
  - `Debounce(TimeSpan, TimeProvider)` — collapse rapid bursts (search box typing).
  - `Timeout(TimeSpan, TimeProvider)` — error/complete if no events within duration.

- **Testing with FakeTimeProvider**
  - Deterministic tests are easy by injecting the fake clock.
    ```csharp
    using Microsoft.Extensions.Time.Testing;
    var fake = new FakeTimeProvider();
    var list = Observable.Timer(TimeSpan.FromSeconds(5), fake).ToLiveList();
    fake.Advance(TimeSpan.FromSeconds(4));
    list.IsCompleted.ShouldBeFalse();
    fake.Advance(TimeSpan.FromSeconds(1));
    list.IsCompleted.ShouldBeTrue();
    ```

- **FrameProvider in WPF**
  - R3 also supports frame-based scheduling (`EveryUpdate`, `IntervalFrame`, `DelayFrame`). WPF has no native frame loop; use only if you introduce a `Dispatcher`-driven frame provider (e.g., via CompositionTarget.Rendering) or rely on the built-in `FakeFrameProvider` for tests.
  - For typical desktop apps, prefer `TimeProvider`-based APIs.

- **Interop with context switching**
  - When time-driven work produces values off the UI thread, use `ObserveOnCurrentSynchronizationContext()` before touching bound properties. Section 7 covers threading in depth.

## 4) BindableReactiveProperty and WPF data binding

- **What it is**
  - `BindableReactiveProperty<T>` bridges R3 and XAML data binding. It implements `INotifyPropertyChanged` (and `INotifyDataErrorInfo` when validation is enabled), exposing a `.Value` property for binding.
  - It is backed by an R3 stream; you can transform/compose values and then call `.ToBindableReactiveProperty(initial)` to expose them to the View.

- **Basic pattern**
  ```csharp
  using R3;

  public sealed class ChatViewModel : IDisposable
  {
      public BindableReactiveProperty<string> MessageInput { get; }
      public BindableReactiveProperty<bool> CanSend { get; }

      private readonly DisposableBag _disposables; // struct, no new required

      public ChatViewModel()
      {
          MessageInput = new BindableReactiveProperty<string>("");

          CanSend = MessageInput
              .Select(text => !string.IsNullOrWhiteSpace(text))
              .ToBindableReactiveProperty(false);
      }

      public void Dispose() => Disposable.Dispose(MessageInput, CanSend);
  }
  ```
  ```xml
  <TextBox Text="{Binding MessageInput.Value, UpdateSourceTrigger=PropertyChanged}" />
  <Button Content="Send" IsEnabled="{Binding CanSend.Value}" />
  ```

- **Read-only exposure**
  - Keep mutable state private and expose `ReadOnlyBindableReactiveProperty<T>` when the View must not set values.
  ```csharp
  private readonly BindableReactiveProperty<int> _unreadMutable = new(0);
  public ReadOnlyBindableReactiveProperty<int> Unread => _unreadMutable;
  ```

- **From observable pipeline**
  ```csharp
  var typing = Observable
      .FromEventPattern<TextChangedEventArgs>(input, nameof(input.TextChanged))
      .Select(_ => input.Text)
      .Debounce(TimeSpan.FromMilliseconds(200), DispatcherTimeProvider.FromCurrentDispatcher())
      .Select(text => text.Trim());

  SearchText = typing.ToBindableReactiveProperty("");
  ```

- **Validation**
  - Enable DataAnnotation or custom validation logic.
  ```csharp
  using System.ComponentModel.DataAnnotations;

  public sealed class ProfileViewModel : IDisposable
  {
      [Required, MinLength(3)]
      public BindableReactiveProperty<string> DisplayName { get; } =
          new BindableReactiveProperty<string>("")
              .EnableValidation<ProfileViewModel>()
              .ForceValidate(); // optional: validate initial

      // Custom validator
      public BindableReactiveProperty<string> PortText { get; } =
          new BindableReactiveProperty<string>("")
              .EnableValidation(text =>
              {
                  return int.TryParse(text, out var p) && p is >= 1 and <= 65535
                      ? null
                      : new Exception("Port must be 1-65535");
              });

      public void Dispose() => Disposable.Dispose(DisplayName, PortText);
  }
  ```
  ```xml
  <TextBox Text="{Binding DisplayName.Value, UpdateSourceTrigger=PropertyChanged}" />
  <ItemsControl ItemsSource="{Binding (Validation.Errors), RelativeSource={RelativeSource Self}}" Visibility="Collapsed"/>
  <!-- Bind WPF validation visuals automatically via INotifyDataErrorInfo -->
  ```

- **Forcing notifications**
  - `.Value = x` suppresses notification if `x` equals the current value; call `.OnNext(x)` to force notify even when equal.

- **Threading**
  - Always push UI-bound values on the UI thread. Either construct the chain with a dispatcher `TimeProvider` or end with `ObserveOnCurrentSynchronizationContext()`.

- **Compared to BehaviorSubject**
  - `ReactiveProperty<T>`/`BindableReactiveProperty<T>` are like `BehaviorSubject<T>` but deduplicate values and integrate with WPF binding and validation.

## 5) ReactiveCommand and commanding

- **What it is**
  - `ReactiveCommand` and `ReactiveCommand<T>` are `ICommand` implementations backed by R3. They expose `CanExecute` as an observable boolean and are themselves observables of execution notifications.

- **Creating commands**
  - From a boolean observable (e.g., `CanSend`):
    ```csharp
    public ReactiveCommand SendCommand { get; }
    SendCommand = CanSend
        .ToReactiveCommand(_ => SendCore()); // non-generic: Unit payload

    void SendCore()
    {
        // mutate state and/or publish to service
        _ = chatService.Send(MessageInput.Value);
        MessageInput.Value = "";
    }
    ```
  - Generic payload:
    ```csharp
    public ReactiveCommand<string> DeleteMessage { get; }
    DeleteMessage = IsConnected
        .ToReactiveCommand<string>(id => chatService.Delete(id));
    ```

- **Async commands**
  - Use `ToReactiveCommand(async _ => await DoAsync())` or combine with `SubscribeAwait` when you want backpressure strategies.
  - Example with `Drop` to prevent double-clicks:
    ```csharp
    public ReactiveCommand SaveProfile { get; }
    SaveProfile = IsValid
        .Select(valid => valid)
        .ToReactiveCommand<Unit>(_ => { }) // create command
        .Also(cmd =>
        {
            cmd.AsObservable()
               .SubscribeAwait(async (_, ct) =>
               {
                   await profileService.SaveAsync(Model, ct);
               }, AwaitOperation.Drop);
        });
    ```

- **Binding in XAML**
  ```xml
  <Button Content="Send" Command="{Binding SendCommand}" />
  <Button Content="Delete" Command="{Binding DeleteMessage}" CommandParameter="{Binding SelectedMessageId}" />
  ```

- **Error handling**
  - If async work throws, prefer catching inside `SubscribeAwait` or convert to completion via `OnErrorResumeAsFailure()` when the command stream should terminate (rare in UI). Otherwise surface to a notification service from `OnErrorResume`.

- **Disposal**
  - Commands are `IDisposable`. Dispose them with the ViewModel to detach all handlers:
    ```csharp
    public void Dispose() => Disposable.Dispose(SendCommand, DeleteMessage);
    ```

- **Notes**
  - Because `ReactiveCommand` integrates with `CanExecute`, it will automatically disable the button when `CanExecute` is false; no manual `RaiseCanExecuteChanged` calls are needed.
  - For commands that must be throttled by time, combine with `ThrottleFirst`/`Debounce` on the command’s observable stream.

## 6) Subscription management in WPF

- **Why this matters**
  - Long‑lived UI processes easily leak subscriptions. R3 optimizes disposables and adds tracking so we can enforce clean lifetimes.

- **Disposable options and when to use**
  - `Disposable.Combine(d1,..,d8)` — fastest when the set is known at construction.
  - `Disposable.CreateBuilder()` — build up in code paths, then `.Build()` into a single `IDisposable`.
  - `DisposableBag` — struct, add‑only, lightweight for accumulating during VM lifetime. Keep as a field and pass by `ref` to `AddTo(ref bag)`.
  - `CompositeDisposable` — thread‑safe, supports `Remove`; use when you need dynamic add/remove from multiple threads.

- **AddTo patterns**
  ```csharp
  public sealed class SessionsSidebarViewModel : IDisposable
  {
      private DisposableBag _bag;

      public SessionsSidebarViewModel(ISessionDirectory directory)
      {
          directory.Sessions()
              .Subscribe(session => /* update state */)
              .AddTo(ref _bag);
      }

      public void Dispose() => _bag.Dispose();
  }
  ```

- **View/ViewModel lifetime**
  - ViewModels should implement `IDisposable` and dispose their bags/commands/subjects in `Dispose()`.
  - Windows/UserControls should dispose their DataContext on close/unload:
    ```csharp
    protected override void OnClosed(EventArgs e)
    {
        (DataContext as IDisposable)?.Dispose();
        base.OnClosed(e);
    }
    ```

- **Subject disposal semantics**
  - Disposing an R3 subject completes observers by default. Prefer this to guarantee teardown of dependent chains when the VM is disposed.
  - If you must keep the subject alive beyond VM scope, avoid disposing the subject and only dispose the subscriptions.

- **Cancelling factories**
  - Time‑based factories accept `CancellationToken`. Couple downstream completion to upstream cancellation with `DoCancelOnCompleted`:
    ```csharp
    var cts = new CancellationTokenSource();
    Observable.Interval(TimeSpan.FromSeconds(1), TimeProvider.System, cts.Token)
        .Take(10)
        .DoCancelOnCompleted(cts)
        .Subscribe(_ => TickCount.Value++ )
        .AddTo(ref _bag);
    ```

- **Tracking leaks (optional)**
  - Enable tracking in dev builds to detect dangling subscriptions:
    ```csharp
    ObservableTracker.EnableTracking = true;
    ObservableTracker.EnableStackTrace = true;
    ObservableTracker.ForEachActiveTask(t => logger.LogDebug("Active: {Task}", t));
    ```

- **Unhandled exceptions pipeline**
  - Register a global handler once (App startup):
    ```csharp
    ObservableSystem.RegisterUnhandledExceptionHandler(ex =>
        appLogger.LogError(ex, "R3 unhandled exception"));
    ```

- **Common leak patterns to avoid**
  - Capturing `this` inside subscriptions without disposing with the VM.
  - Subscribing in code‑behind without a disposal path.
  - Creating `Subject`s in views instead of VMs and not disposing them.

## 7) Threading and synchronization in WPF

- **UI thread as the authority**
  - WPF requires that bound properties be updated on the UI thread. Ensure the tail of any pipeline that sets `.Value` runs on the dispatcher thread.

- **ObserveOn vs SubscribeOn**
  - `ObserveOnCurrentSynchronizationContext()` — switch the downstream observer to the UI context. Use this before touching `.Value`.
  - `SubscribeOn...` — controls where the subscription side-effects run; less commonly needed in WPF but useful for heavy initializations.

- **Dispatcher interop**
  ```csharp
  Observable.FromAsync(ct => service.FetchAsync(ct))
      .SubscribeOnThreadPool()              // perform work on thread pool
      .ObserveOnCurrentSynchronizationContext() // then marshal to UI
      .Subscribe(result => UiState.Value = result);
  ```

- **Gate synchronization for multi-threaded sources**
  - Operators assume single-threaded `OnNext`. If a source may call `OnNext` concurrently (e.g., event raised from multiple threads), serialize with `Synchronize`.
  ```csharp
  var gate = new object();
  externalSubject
      .Synchronize(gate)
      .Where(x => x.IsValid)
      .ObserveOnCurrentSynchronizationContext()
      .Subscribe(x => Items.Add(x));
  ```

- **Subject thread-safety nuances**
  - `Subject` is not thread-safe for `OnNext`; if multiple threads push, guard with a lock or `Synchronize`.
  - `BehaviorSubject` and `ReplaySubject` are thread-safe, including `OnNext`.
  - `ReactiveProperty`/`BindableReactiveProperty` are not thread-safe; do not call `.Value` setters and `.Subscribe` concurrently from multiple threads.

- **TimeProvider and context**
  - A `DispatcherTimeProvider` executes timer callbacks on the UI thread. Prefer passing it to time-based operators when the output updates UI state.

- **Common recipes**
  - Background -> UI binding:
    ```csharp
    Observable.Timer(TimeSpan.FromSeconds(1))
        .SubscribeOnThreadPool()
        .Select(_ => DateTimeOffset.Now)
        .ObserveOnCurrentSynchronizationContext()
        .Subscribe(now => ClockText.Value = now.ToString("T"));
    ```
  - Burst events -> debounce on UI thread:
    ```csharp
    SearchTextChanged
        .Select(_ => Input.Value)
        .Debounce(TimeSpan.FromMilliseconds(250), DispatcherTimeProvider.FromCurrentDispatcher())
        .Subscribe(text => RunQuery(text));
    ```

## 8) Testing R3 in Desktop.Wpf

- **Clock control with FakeTimeProvider**
  - Replace real time with `FakeTimeProvider` to deterministically advance timers.
  ```csharp
  using Microsoft.Extensions.Time.Testing;
  using R3;

  [Fact]
  public void Debounce_SearchText_WaitsForIdle()
  {
      var fake = new FakeTimeProvider();
      var ui = fake; // ViewModel uses injected TimeProvider

      var vm = new SearchVm(ui);
      vm.Input.Value = "N"; fake.Advance(TimeSpan.FromMilliseconds(100));
      vm.Input.Value = "Ne"; fake.Advance(TimeSpan.FromMilliseconds(100));
      vm.Input.Value = "Neo"; // not yet emitted

      Assert.Equal("", vm.LastQuery.Value);
      fake.Advance(TimeSpan.FromMilliseconds(250));
      Assert.Equal("Neo", vm.LastQuery.Value);
  }
  ```

- **Frame control with FakeFrameProvider**
  - For frame APIs (`EveryUpdate`, `IntervalFrame`), use the built-in `FakeFrameProvider`.
  ```csharp
  [Fact]
  public void EveryUpdate_PushesEachAdvance()
  {
      var frames = new FakeFrameProvider();
      var xs = Observable.EveryUpdate(frames).ToLiveList();
      frames.Advance();
      frames.Advance(2);
      xs.Count.ShouldBe(3);
  }
  ```

- **LiveList assertions**
  - Convert a stream to `LiveList<T>` for simple, allocation-free testing.
  ```csharp
  var list = source.Select(x => x*2).ToLiveList();
  list.AssertEmpty();
  sourceSubject.OnNext(1);
  list.AssertEqual(2);
  sourceSubject.OnCompleted();
  list.AssertIsCompleted();
  ```

- **ViewModel unit testing pattern**
  - Inject dependencies and `TimeProvider`/`FrameProvider`. Avoid WPF `Dispatcher` in unit tests; assert on reactive state only.
  - Don’t test XAML; test public observable behavior of the ViewModel (bindings reflect via `.Value`).

## 9) Migration from System.Reactive/UniRx to R3 (WPF)

- **Conceptual changes**
  - `OnError` becomes `OnErrorResume` and does NOT tear down; terminal completes use `OnCompleted(Result)`.
  - `IScheduler` -> `TimeProvider` (and optionally `DispatcherTimeProvider` in WPF). Replace scheduler args with a `TimeProvider` parameter.
  - Many single-result methods are now `***Async` returning `Task<T>` (e.g., `FirstAsync`, `LastAsync`).

- **Operator name mapping**
  - `Throttle` -> `Debounce`
  - `Sample` -> `ThrottleLast`
  - `StartWith` -> `Prepend`
  - `Buffer` -> `Chunk`
  - `Amb` -> `Race`
  - `ThrottleFrame` -> `DebounceFrame`, `SampleFrame` -> `ThrottleLastFrame`

- **Subjects**
  - R3 subjects call `OnCompleted` on `Dispose()` by default. If you relied on keeping observers alive after disposal, switch to not disposing the subject or pass `Dispose(false)` explicitly.

- **Threading changes**
  - Replace `ObserveOn(DispatcherScheduler.Current)` with `ObserveOnCurrentSynchronizationContext()` or prefer `DispatcherTimeProvider` in time-based operators.

- **Interop bridge**
  - Wrap legacy pipelines when needed:
    - `IObservable<T>.ToObservable()` -> R3 `Observable<T>`
    - `Observable<T>.AsSystemObservable()` -> `IObservable<T>`

- **Commands**
  - UniRx `ReactiveCommand` maps to R3 `ReactiveCommand`; switch creation helpers to R3’s `ToReactiveCommand` and prefer `SubscribeAwait` for async handlers.

- **Disposables**
  - Prefer `DisposableBag` or `Disposable.CreateBuilder()` over `CompositeDisposable` for performance unless you need thread-safe `Remove`.

- **Tests**
  - Replace `TestScheduler` usages with `FakeTimeProvider` and `LiveList`.

## 10) Practical recipes for Desktop.Wpf

- **Sidebar search (debounce + filter)**
  ```csharp
  SearchText = new BindableReactiveProperty<string>("");
  var ui = DispatcherTimeProvider.FromCurrentDispatcher();
  Filtered = SearchText
      .Select(x => x.Trim())
      .Debounce(TimeSpan.FromMilliseconds(250), ui)
      .SelectAsync(async (text, ct) => await directory.FilterAsync(text, ct))
      .ObserveOnCurrentSynchronizationContext()
      .ToBindableReactiveProperty(Array.Empty<SessionListItem>());
  ```

- **Chat send flow**
  ```csharp
  MessageInput = new("");
  CanSend = MessageInput.Select(t => !string.IsNullOrWhiteSpace(t)).ToBindableReactiveProperty(false);
  SendCommand = CanSend.ToReactiveCommand(_ => { });
  SendCommand.AsObservable()
      .SubscribeAwait(async (_, ct) =>
      {
          await chat.SendAsync(MessageInput.Value, ct);
          MessageInput.Value = "";
      }, AwaitOperation.Drop);
  ```

- **Inbound messages from background bus**
  ```csharp
  bus.InboundMessages
     .ObserveOnCurrentSynchronizationContext()
     .Subscribe(msg => Messages.Add(msg))
     .AddTo(ref bag);
  ```

- **Retry and backpressure strategies**
  ```csharp
  RefreshCommand = IsOnline.ToReactiveCommand(_ => { });
  RefreshCommand.AsObservable()
      .SubscribeAwait(async (_, ct) =>
      {
          var retries = 0;
        AGAIN:
          try { await service.RefreshAsync(ct); }
          catch when (retries++ < 3) { goto AGAIN; }
      }, AwaitOperation.Drop);
  ```

- **Progress throttling for UI**
  ```csharp
  service.Progress
      .ThrottleLast(TimeSpan.FromMilliseconds(100), DispatcherTimeProvider.FromCurrentDispatcher())
      .Subscribe(p => Progress.Value = p);
  ```

- **Toast on pipeline errors without teardown**
  ```csharp
  pipeline
      .Do(onErrorResume: ex => toasts.ShowError(ex.Message))
      .Subscribe();
  ```

- **Leak‑proof VM disposal template**
  ```csharp
  public sealed class Vm : IDisposable
  {
      private DisposableBag _bag;
      public void Dispose() => _bag.Dispose();
  }
  ```
