# Domain-Driven Design & Persistence: Signal-Style Group Management

This document outlines the architecture for a secure, private group messaging system based on the Signal Protocol (specifically "Private Groups"). The core architectural principle is **Zero-Knowledge Server**. The server does not know who is in the group, who the admins are, or the group's name. All group logic is handled client-side via signed, end-to-end encrypted administrative messages.

---

## 1. The Domain Model (DDD)

In this context, the **Client Application** acts as the host for the Domain logic. The Server is merely a dumb pipe.

### Bounded Context: Group Administration

#### Aggregate Root: `PrivateGroup`
The `PrivateGroup` aggregate ensures the consistency of the group's state on the local device. It enforces invariants like "Only admins can add members" and "Group state must be cryptographically verifiable."

**State:**
* `GroupId` (Value Object): A random 128-bit identifier generated by the creator.
* `MasterKey` (Value Object): The secret key used to derive attributes like the group topic/avatar encryption key.
* `Members` (Collection of Entities): The current roster.
* `SequenceNumber` (Value Object): Monotonically increasing counter to order changes.

**Behaviors (Methods):**
* `CreateGroup(initialMembers)`: Generates the Genesis state.
* `ProcessIncomingChange(signedChangePayload)`: Validates a signature, checks the sequence, and mutates the state.
* `AddMember(newMemberIdentity)`: Generates a signed "Add" command.
* `RemoveMember(targetIdentity)`: Generates a signed "Remove" command and triggers a **Sender Key Rotation**.

#### Entity: `GroupMember`
Represents a participant in the group.
* `IdentityKey` (Value Object): The public X3DH identity key of the user.
* `Role` (Value Object): Enum [`Member`, `Administrator`].

#### Value Object: `GroupChangeProposal`
This is the payload sent over the wire. It represents a transition in state.
* `ChangeType`: (Add, Remove, Promote, Demote, UpdateTitle).
* `Args`: The data (e.g., the new title, or the identity key of the added user).
* `EditorIdentity`: The Admin making the change.
* `Signature`: The cryptographic proof authorizing the change.

## 2. The Workflows

### A. Group Creation (The Genesis)
1.  **Alice (Creator)** generates a random `GroupId` and `MasterKey`.
2.  Alice constructs a `GroupState` object containing herself as the first Admin.
3.  Alice signs this state with her private Identity Key.
4.  Alice sends a **1:1 pairwise encrypted message** (using the existing Double Ratchet session) to Bob and Charlie.
    * *Payload:* `GroupId`, `MasterKey`, `InitialState`, `Signature`.
5.  Bob and Charlie receive the message, verify Alice's signature, and instantiate the `PrivateGroup` aggregate locally.

### B. Adding a Member
1.  **Alice (Admin)** wants to add David.
2.  Alice creates a `GroupChange` command: `AddMember(David)`.
3.  Alice increments the group's `SequenceNumber`.
4.  Alice **signs** this command with her private Identity Key.
5.  Alice sends this signed command encrypted 1:1 to Bob, Charlie, and David.
6.  **Recipients** verify Alice is a current Admin in their local state, verify the signature, and apply the change.

### C. Removing a Member (Key Rotation)
1.  **Alice (Admin)** wants to remove Bob.
2.  Alice sends a signed `RemoveMember(Bob)` message to Charlie and David (but *not* Bob).
3.  **Crucial Step:** Alice initiates a **Sender Key Rotation**.
    * The underlying encryption for group messages uses "Sender Keys" (a key Alice pushes to others so they can decrypt her broadcasts).
    * Because Bob has the old keys, Alice must generate a *new* random Sender Key.
    * She distributes this new key to Charlie and David 1:1.
    * She does *not* give it to Bob.
4.  Future messages from Alice are encrypted with the new key, which Bob cannot read.

## 3. Persistence Model (SQLite)

The client needs to persist the current state for UI and logic, and the cryptographic state for messaging.

### Table: `groups`
Stores the high-level metadata and current state of the aggregate.

```sql
CREATE TABLE groups (
    group_id BLOB PRIMARY KEY,          -- Random GUID/Bytes
    master_key BLOB NOT NULL,           -- Secret key for deriving attribute keys
    title TEXT,                         -- Decrypted title
    sequence_number INTEGER DEFAULT 0,  -- Handling out-of-order updates
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    is_active BOOLEAN DEFAULT 1         -- If we left/were removed
);
```

### Table: `group_members`
A relational mapping of who is currently in the group and their role.

```sql
CREATE TABLE group_members (
    group_id BLOB,
    identity_key BLOB,                  -- The member's public Identity Key
    role INTEGER,                       -- 0 = Member, 1 = Admin
    joined_at_sequence INTEGER,         -- Which seq number added them
    PRIMARY KEY (group_id, identity_key),
    FOREIGN KEY (group_id) REFERENCES groups(group_id)
);
```

### Table: `group_action_log` (Optional but Recommended)
An event log. Useful for calculating the "Safety Number" state or auditing "Who changed the group name?".

```sql
CREATE TABLE group_action_log (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    group_id BLOB,
    editor_identity_key BLOB,           -- Who made the change
    action_type TEXT,                   -- 'ADD', 'REMOVE', 'TITLE_CHANGE'
    action_data BLOB,                   -- Protobuf blob of the change details
    signature BLOB,                     -- The cryptographic proof
    sequence_number INTEGER,
    received_at TIMESTAMP,
    FOREIGN KEY (group_id) REFERENCES groups(group_id)
);
```

### Table: `sender_keys`
This stores the cryptographic material. In Signal groups, you don't Double Ratchet with every member. You maintain a "Sender Key" for every member.

* **My Sender Key:** The key *I* use to encrypt messages. I send this to everyone else.
* **Their Sender Keys:** The keys I have received from Bob, Charlie, etc., used to decrypt *their* messages.

```sql
CREATE TABLE sender_keys (
    group_id BLOB,
    sender_identity_key BLOB,           -- Who owns this key
    device_id INTEGER,                  -- Signal allows multi-device
    chain_key BLOB,                     -- Current chain key state
    signing_key BLOB,                   -- Used to sign individual messages
    PRIMARY KEY (group_id, sender_identity_key, device_id),
    FOREIGN KEY (group_id) REFERENCES groups(group_id)
);
```

## 4. Protobuf Definitions (Data Transfer)

These are the messages exchanged inside the 1:1 encrypted tunnels.

```protobuf
syntax = "proto3";

// The payload sent to update the group
message GroupUpdateMessage {
    bytes group_id = 1;
    uint32 sequence_number = 2;
    
    oneof update {
        ChangeMember update_members = 3;
        UpdateTitle update_title = 4;
        UpdateAvatar update_avatar = 5;
    }

    // The signature of the above data by the Admin
    bytes signature = 6; 
}

message ChangeMember {
    // List of members to add or remove
    repeated MemberOperation operations = 1;
}

message MemberOperation {
    bytes member_identity_key = 1;
    enum Action {
        ADD = 0;
        REMOVE = 1;
        PROMOTE_ADMIN = 2;
        DEMOTE_ADMIN = 3;
    }
    Action action = 2;
}

message UpdateTitle {
    string new_title = 1;
}

// Distribution of the Sender Key (Encryption Material)
// Sent when joining or after rotation
message SenderKeyDistribution {
    bytes group_id = 1;
    bytes sender_key_chain = 2;
    bytes sender_signing_key = 3;
}
```
